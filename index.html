ICWE 2026 – Poster Track

A State-Based Add-Wins CRDT for RDF Datastores

Jitse De Smet, Ruben Taelman IDLab, Dept. of Electronics and Information Systems, Ghent University – imec

1 Problem

  • Decentralized ecosystems (Solid, IDSA, Gaia-X) have no central coordinator — agents write to shared RDF knowledge graphs concurrently
  • Offline / disconnected editing leads to divergent local states and write conflicts upon reconnection
  • Existing CRDT approaches suffer a consistency boundary problem or require extra infrastructure beyond standard Web stacks

2 Approach

  • Model an OR-Set CRDT entirely in RDF 1.2 triple terms — bookkeeping lives inside the dataset itself
  • Add-wins semantics: a concurrent add and remove of the same triple keeps the triple present
  • Transparent to unaware SPARQL agents — they see only the correct logical view via a dedicated named graph

3 Background & Related Work

CRDTs (Conflict-free Replicated Data Types) guarantee eventual consistency without coordination. State-based CRDTs merge by computing a join in a join-semilattice.
OR-Set (Observed-Remove Set) is a CRDT where add-tags track additions; a tombstone set records removals. Add-wins when tags conflict.
RDF 1.2 Triple Terms allow reification of triples as first-class resources, enabling per-triple metadata — used here to attach add-tags to triples.
Solid and similar decentralized data platforms expose RDF resources over HTTP. No CRDT support is assumed on the server side.

4 RDF 1.2 Data Model

  • Each triple gets one or more add-tags (UUIDs) stored in crdt:tags named graph via blank-node reification
  • Removing a triple moves its add-tags to the tombstone named graph (crdt:tombstones)
  • A triple is present iff at least one of its add-tags is not in the tombstone set
  • Merge = union of add-tag graphs + union of tombstone graphs. The visible state graph is recomputed deterministically

5 Web Synchronization

  • State-based replication — agents exchange the full CRDT state, no operation log required
  • Uses standard HTTP ETags + If-Match to prevent mid-air collisions; server performs the merge on PUT
  • Compatible with any RDF-over-HTTP server (e.g. a Solid pod) — no custom protocol needed
  • CRDT-aware and unaware clients coexist — unaware clients query the logical view graph transparently

6 Tombstone GC

  • NTP clock drift bounded at ≤ 2000 ms
  • Add-tags encode a timestamp (stamp-uuid) at creation time
  • Tombstone safe to prune after d + 4 000 s where d is the deletion time
  • Works in open ecosystems with untrusted NTP clocks

7 Conclusion

  • Conflict-free RDF replication modelled entirely in RDF 1.2 — no opaque blobs
  • No consistency boundary problem: CRDT bookkeeping is in the same RDF dataset
  • Deployable on standard Solid pods using only HTTP semantics
  • PoC implementation: ORset-RDF-store

8 Future Work

  • Constraint-aware merge semantics
  • Two valid states can merge into a constraint-violating state — needs resolution strategy
  • Performance benchmarking at scale
Conflict-free RDF replication using only standard Web infrastructure — no extra servers, no boundary problem.
