1Introduction

  • ─ In decentralized data ecosystems (Solid, IDSA, Gaia-X), multiple agents read from and write to shared RDF knowledge graphs concurrently.
  • ─ When agents independently modify the same resource while offline, their updates collide once connection is restored.
  • ─ CRDTs (Conflict-free Replicated Data Types) guarantee convergence through well-defined merge algorithms, with no coordination required.
  • ─ RDF 1.2 triple terms enable first-class modelling of state-based CRDTs directly within RDF datasets, without external bookkeeping.

2Related Work

  • ─ m-ld — JavaScript CRDT engine for RDF, but requires a dedicated domain server.
  • ─ Gruss et al. — RDF state + binary CRDT blob (Yjs/Automerge); introduces a consistency boundary problem.
  • ─ SU-Set — extends OR-Set for RDF but uses an operation-based approach.
  • ─ We adopt the state-based OR-Set which aligns naturally with HTTP REST semantics — exchanging full dataset state rather than individual operations.

3State-based Add-Wins OR-Set in RDF 1.2

Each RDF triple carries a set of unique add-tags (UUIDv4). Removing a triple moves its tags to a tombstone set rather than deleting them — ensuring a concurrent add always wins.

RDF 1.2 triple terms allow a triple to appear in the object position of another triple, enabling all bookkeeping within the same dataset — no external infrastructure needed.

A triple is present when it has at least one add-tag not in its tombstone set. On merge, identifying nodes for the same triple are consolidated.

5NTP Tombstone Optimization

Without garbage collection, tombstones accumulate indefinitely.

We exploit NTP synchronization: since NTP panics after >1000s drift, any two synchronized clients differ by at most 2000s.

A tag is universally seen once its timestamp is older than d + 4000s, enabling safe pruning without knowing the replica set.

6Key Properties

  • ─ No infrastructure beyond RDF-over-HTTP + ETag
  • ─ All bookkeeping inside the dataset — no consistency boundary
  • ─ CRDT-aware and unaware clients coexist
  • ─ Transparent to SPARQL query engines
  • ─ PoC implementation: orset-rdf-store

7Conclusion & Future Work

A state-based add-wins set CRDT modelled entirely in RDF 1.2, requiring no infrastructure beyond RDF-over-HTTP with ETag support.

By abstracting at the quad-store level, the CRDT can be plugged into existing query engines, making conflict resolution fully transparent.

Future work: constraint-aware merge semantics for RDF CRDTs.
