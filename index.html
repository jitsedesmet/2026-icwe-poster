Client-Driven Offline-First RDF 1.2 using OR-Sets

Jitse De Smet, Ruben Taelman

IDLab, Department of Electronics and Information Systems, Ghent University – imec, Belgium

1Problem

In decentralized data ecosystems (Solid, IDSA, Gaia-X), multiple agents read from and write to shared RDF knowledge graphs concurrently — even while offline.
When two agents independently modify the same resource while offline, their updates collide once connection is restored.
How can we achieve conflict-free convergence without dedicated infrastructure — using only what the Web already provides?
CRDTs (Conflict-free Replicated Data Types) guarantee convergence through well-defined merge algorithms, with no coordination required.

2Related Work

m-ld — JavaScript CRDT engine for RDF, but requires a dedicated domain server.
Gruss et al. — RDF state + binary CRDT blob (Yjs/Automerge); introduces a consistency boundary problem where a standard HTTP server cannot atomically update multiple resources.
SU-Set — extends OR-Set for RDF but uses an operation-based approach.
We adopt the state-based OR-Set which aligns naturally with HTTP REST semantics — exchanging full dataset state rather than individual operations.

3State-based Add-Wins OR-Set in RDF 1.2

Each RDF triple carries a set of unique add-tags (UUIDv4). Removing a triple moves its tags to a tombstone set — ensuring a concurrent add always wins.

RDF 1.2 triple terms allow a triple to appear in the object position of another triple, enabling all bookkeeping within the same dataset — no external infrastructure needed.

A triple is present when it has at least one add-tag not in its tombstone set. On merge, identifying nodes for the same triple are consolidated.

5NTP Tombstone Optimization

Without garbage collection, tombstones accumulate indefinitely. Existing solutions require causal delivery and a known replica set — assumptions that fail in open ecosystems.

We exploit NTP synchronization: since NTP panics after >1000s drift, any two synchronized clients differ by at most 2000s. A tag is universally seen once its timestamp is older than d + 4000s, enabling safe pruning without knowing the replica set.

6Key Properties

No infrastructure beyond RDF-over-HTTP + ETag
All bookkeeping inside the dataset — no consistency boundary
CRDT-aware and unaware clients coexist
Transparent to SPARQL query engines

7Conclusion & Future Work

A state-based add-wins set CRDT modelled in RDF 1.2, pluggable into existing query engines. Future work: constraint-aware merge semantics.
